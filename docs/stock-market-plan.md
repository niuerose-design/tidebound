## 0. 구현 결과 (v3.213, 공유 시장)

- **개인 vs 공유 부하 비교 결론:** DB · 요청 수 · 전송량은 같습니다(둘 다 DB 0, 원래 `sync`에 새 틱만 얹기, 브라우저 저장). 부하를 줄인 건 'sync에 얹기 + 브라우저 저장'이라 둘 다 씁니다.

- 위치: 왼쪽 메뉴의 '증권거래소'(상점과 따로, `view: 'market'`).

  시세는 계속 흐르고 매수 · 매도만 막습니다. 설정은 다른 서버 설정과 같은 30초 캐시로 읽어(추가 DB 읽기는 30초에 1번) 다른 인스턴스엔 최대 30초 뒤 반영됩니다. 화면은 거래소를 볼 때 동기화 응답의 `marketStatus`로 배너를 띄우고 버튼을 막습니다.
- 상한을 없앤 영향: 거래 한 번은 다른 행동과 같은 세이브 쓰기 1번이라 서버 쪽 제한은 기존 행동과 같습니다. 대신 이익 · 손실이 넣은 주화에 비례하므로, 공략 기대 수익(아래 점검의 '1σ 아래 사서 하루' 최대 약 +2%)이 큰 주화에 그대로 곱해집니다. 주화 인플레이션이 보이면 수수료 · σ를 올립니다.
- 수치 변경: 평균 회귀가 빠르면 '싸게 사서 하루 들기'가 크게 남아 λ = 0.9995(반감기 약 10일) · warm 9,000틱 · 볼록성 보정(−σ²/2)으로 바꾸고 σ를 낮췄습니다. 시작점은 144틱 묶음마다 맞춰 차트와 체결 가격이 늘 같습니다.
- 점검: `node scripts/check-market.mjs` — 수수료 뺀 기대 수익(아무 때나 하루 −1~−2%, 1σ 아래 사서 하루 최대 약 +2%, 소문 따라 한 틱 −1.8~−2%). 기준(1% · 5% · 0%)을 넘으면 실패합니다.

## 3. 서버 부하 0을 만드는 핵심 설계

> v2(2026-10-09): **개인 시장**으로 바꿨습니다. 종목은 모두 같지만, 시세는 모험가(캐릭터 슬롯)마다 다르게 흐릅니다.
> 전투 기록처럼 '나만의 기록'이 되고, 다른 유저와 시세가 겹치지 않습니다.

### 3-1. 시세는 저장하지 않는다 (개인별 결정론적 계산)

- 시간을 10분 칸(틱)으로 나눕니다: `tick = floor(now / 10분)`.
- 모험가 시드: `seed = hash(MARKET_SECRET, 모험가 ID)`. 모험가 ID는 슬롯까지 구분합니다(`계정#2`, `game/server/store.ts` `playerId`).
- 각 틱의 충격값 `ε(종목, tick) = hash(seed, 종목 id, tick)` → 정규분포 근사값(-3~+3).
- 로그 가격은 평균으로 돌아가는 AR(1) 과정: `logP(t) = λ · logP(t-1) + σ · ε(t)` (λ = 0.98, 기준가로 끌려옴)
- 어떤 시각의 가격이든 **그 시각 300틱 전부터 0으로 시작해 돌리면** 같은 값이 나옵니다(λ³⁰⁰ ≈ 0.002라 시작점 영향이 사라짐).
  → 어느 서버 인스턴스에서 계산해도 그 모험가에게는 같은 가격, **시세 기록 저장 0**. 종목 6개 × 444틱 ≈ 2,700번 해시 = 1ms 미만.
- 가격 = `기준가 × exp(logP)`, 기준가의 0.2배~5배로 자릅니다.

### 3-2. 왜 시세 계산을 브라우저로 옮기지 않는가

- 브라우저가 시드와 계산식을 가지면 **미래 가격을 미리 계산**할 수 있습니다(개인 시장이어도 같음).
- 체결은 서버가 해야 하므로(주화가 오감) 서버도 같은 가격을 알아야 하고, 그러려면 시드를 서버만 가져야 합니다.
- 그래서 `MARKET_SECRET`은 **서버 전용 환경 변수**(또는 `game/secret/`)에만 두고, 화면에는 **지금 틱까지의 가격만** 보냅니다.

### 3-3. 시세 전송: 원래 동기화에 얹기 (새 요청 0)

- 개인마다 시세가 달라 공용 CDN 캐시는 못 씁니다. 대신 **원래 보내는 `sync`** 에 얹습니다.
  - 거래소 화면이 열려 있을 때만 `sync` 요청에 `market: <내가 가진 마지막 틱>` 을 붙입니다.
  - 서버는 그 뒤의 틱만 돌려줍니다. 보통 0개(같은 틱) 또는 1개(종목 6개 = 숫자 6개 + 소문 1줄).
  - 처음 열 때만 최근 144틱(하루, 약 5KB)을 한 번 보냅니다. 카탈로그 키(`catalogKey`)를 다시 안 보내는 방식과 같습니다.
- DB 접근 0, 새 요청 0, 서버 CPU는 화면을 연 동안 동기화마다 1ms 미만.

### 3-4. 전투 기록처럼 브라우저에만 남기는 것

전투 기록(`components/game/battle-records.ts`)은 이미 받은 로그를 이 브라우저의 localStorage에만 남기고 서버에 보내지 않습니다. 거래소도 같은 방식을 최대한 씁니다.

| 데이터 | 저장 위치 | 이유 |
|---|---|---|
| 지난 시세(차트) | **브라우저(localStorage)** | 받은 틱을 쌓아 두고 다시 받지 않음. 지우면 다음에 하루치만 다시 받음 |
| 거래 내역 · 손익 그래프 · 관심 종목 · 화면 설정 | **브라우저(localStorage)** | 보기용 기록이라 조작돼도 주화에 영향 없음 |
| 보유 수량 · 매수 원금 · 오늘 거래 수 · 누적 실현 손익 | **서버 세이브** | 주화가 오가는 판정이라 브라우저에 두면 안 됨 |

- 보유 주식까지 브라우저에 두면: 손해 본 뒤 localStorage 되돌리기 · 지우기, 기기 두 대에서 같은 주식 두 번 팔기, 수량 고쳐 쓰기로 주화를 복사할 수 있습니다.
  서버 서명 영수증으로 막아도, 같은 영수증을 두 번 못 쓰게 하려면 결국 서버가 사용 기록을 남겨야 해서 아래 방식(약 200바이트)보다 이득이 없습니다.
- 브라우저 기록은 기기마다 따로이고 브라우저 데이터를 지우면 사라집니다(전투 기록과 같은 안내 문구). 시세 자체는 서버 계산식이라 사라지지 않습니다.

### 3-5. 보유 주식은 세이브에

```ts
// game/types.ts State에 추가
market?: {
    holdings: Record<string, { qty: number; cost: number }>; // 종목 → 수량 · 매수 원금 합(주화)
    day?: string; trades?: number;                            // 오늘(한국 시간) 거래 수
    realized?: number;                                        // 누적 실현 손익(통계 · 칭호용)
};
```

- 세이브는 원래 동기화마다 읽고 쓰므로, 이 몇 줄로 늘어나는 DB 비용은 거의 0입니다.
- 매수 · 매도 = 행동 `{ type: 'market', id: '<종목>', value: '+N' | '-N' }`. 서버가 **행동을 처리하는 순간의 틱 가격**으로 체결합니다(화면이 보낸 가격은 믿지 않음).
- 거래 요청을 더 줄이는 안(선택): 주문을 화면에 모아 두었다가 **다음 `sync`에 실어 보냅니다**. 따로 보내는 요청이 0이 됩니다.
  체결은 서버가 받은 시각의 틱 가격, 화면에는 '다음 동기화 때 체결'로 표시(틱이 바뀌었으면 바뀐 가격으로 체결).
- 부재중에도 시세는 계산식대로 흘러가므로 따로 정산할 것이 없습니다. 팔 때 한 번 계산하면 끝.

### 3-6. 부하 비교

| 항목 | 공용 시장(v1) | 개인 시장(v2, 지금 안) |
|---|---|---|
| DB 표 · 예약 작업 · 웹소켓 | 없음 | 없음 |
| 시세 전송 | 새 엔드포인트, 10분당 함수 1회(CDN) | **새 요청 0**(원래 `sync`에 수십 바이트) |
| 시세 계산 | 10분당 1회 | 화면을 연 유저의 동기화마다 1ms 미만 |
| 매수 · 매도 | 세이브 읽기 1 · 쓰기 1(하루 20회), 또는 `sync`에 실어 0 | 같음 |
| 세이브 크기 | 약 200바이트 | 같음 |

- 결론: 두 방식 모두 DB 부하는 0에 가깝습니다. 개인 시장은 엔드포인트 하나를 덜 만들고, 시세 기록을 브라우저가 쌓으니 전송량도 더 작습니다.
  대신 공용 캐시를 못 써서 계산이 유저 수만큼 돌지만, 1ms 미만이라 무시할 수준입니다.

### 3-7. 개인 시장이라 생기는 차이

- 장점: 다른 유저와 시세 · 소문이 겹치지 않아 '공략 공유'로 모두가 같은 종목을 사는 일이 없습니다. 각자 자기 차트를 가집니다.
- 단점: 채팅에서 "지금 페리온 광산 올랐다" 같은 대화가 안 통합니다. 수익률 랭킹은 서로 다른 시장이라 운 비교에 가깝습니다(9장 6번).
- 슬롯마다 시세가 다르지만 주화도 슬롯별이라 슬롯끼리 주고받는 악용은 없습니다.
- 선택: 승천 횟수를 시드에 넣어 승천하면 시장이 새로 시작되게 할 수 있습니다.

## 5. 재미 요소: 시황 소문

- 틱마다 해시로 '소문'을 만듭니다(예: "페리온 광산에서 새 광맥 소문"). 소문은 **다음 틱 충격의 부호를 70% 확률로 맞힙니다**.
- 소문도 서버가 지금 틱까지만 보내므로, 미리 알 수 있는 건 '다음 10분의 경향 70%'뿐. 수수료(6장)보다 기대 이익이 작게 맞춰 '정답 공략'이 생기지 않게 합니다.
- 선택: 서버 이벤트(`events-config.ts`)나 해킹(`hacks.ts`)과 연결 — 예: 해커의 '시세 조작' 효과. 1차 범위에서는 뺍니다.

## 6. 경제 균형 (주화 인플레이션 방지)

던전 주화는 칠흑 · 코어 · 장비 상자로 바뀌는 성장 재화라, 거래소가 **주화를 찍어내는 곳이 되면 안 됩니다**.

- 기대 수익 0: 평균 회귀 과정이라 오래 들고 있어도 평균은 기준가. 수수료가 있으니 기대값은 약간 마이너스(=주화 소각처).
- 수수료: 매수 · 매도 각 1%(최소 1주화). 소문 적중률 70% × 평균 변동으로 얻는 기대 이익이 왕복 수수료 2%보다 작게 맞춥니다(구현 때 시뮬레이션 스크립트로 확인).
- 투자 한도: 총 보유 원금 최대 **3,000주화**(헬 하루 보너스 약 2.5일분). 큰 이익 · 큰 손실 모두 며칠 수입 안으로 묶습니다.
- 하루 거래 20회(한국 시간 자정 초기화). 세이브 쓰기 횟수도 함께 묶입니다.
- 가격 하한 0.2배: 고위험 종목도 원금 전부를 잃지는 않습니다('상장폐지'는 9장에서 결정).

## 7. 승천 · 환생 · 슬롯

- 환생: 보유 주식 유지(주화와 같음).
- 승천: 주화처럼 **보유 주식도 사라집니다**(승천 직전 매도 안내 문구를 승천 확인창에 추가).
- 캐릭터 슬롯마다 따로(주화가 슬롯별이라 같음).

## 8. 화면

- 위치: 던전 탭 → '주화 상점' 옆에 '증권거래소' 카드(또는 던전 주화 상점 패널 안 탭).
- 종목 목록: 현재가 · 오늘 등락률 · 미니 차트(브라우저에 쌓인 틱, 스파크라인).
- 종목 상세: 하루 차트, 지금 소문, 보유 수량 · 평균 단가 · 평가 손익, 매수 · 매도 수량 입력과 수수료 미리보기.
- 다음 시세 갱신까지 남은 시간(화면 타이머, 서버 호출 없음).
- 기록: 오늘 거래 수, 누적 실현 손익. 선택: 누적 손익 업적 · 칭호('개미', '큰손').

## 9. 결정할 것

1. **v3.208에서 랜덤게임을 지운 이유와 겹치지 않는지.** 판돈형 콘텐츠를 피하려는 것이었다면, 이 거래소도 같은 판단을 받을 수 있습니다.
2. 투자 한도(3,000주화) · 하루 거래 수(20) · 수수료(1%) 수치.
3. 시세 갱신 간격: 10분(권장) / 30분 / 1시간. 짧을수록 자주 들르는 재미, 길수록 덜 피곤함.
4. 소문 기능을 1차에 넣을지.
5. 고위험 종목 '상장폐지'(드물게 가치 0) 이벤트 여부.
6. 랭킹(주간 수익률)을 넣을지. 개인 시장이라 시세가 서로 달라 운 비교에 가깝습니다. 넣으면 기존 랭킹 저장소에 주 1회 · 변화 있을 때만 올립니다.
7. 주문을 `sync`에 실어 보낼지(요청 0, 체결이 최대 1분 늦음) / 바로 보낼지(요청은 주화 상점과 같음, 하루 20회).

## 10. 구현 순서 (결정 뒤)

1. `game/data/market.ts`(종목 · 수치) · `game/server/market.ts`(비밀 시드 · 가격 계산) · `scripts/check-market.mjs`(기대 수익 · 소문 공략 시뮬레이션).
2. `sync`에 시세 얹기(마지막 틱 이후만) · 행동 `market`(체결 · 한도 · 수수료) · 승천 처리 · 마이그레이션.
3. 화면(`components/game/market-panel.tsx`) · 브라우저 시세 · 거래 기록 저장(`components/game/market-records.ts`, 전투 기록 방식) · 가이드 · 업데이트 내역.
