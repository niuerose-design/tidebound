# 렉 · 지연 점검 (v3.91~)

> 작성 2026-10-06. 코드를 읽고 추정한 값입니다(운영 환경에서 시간을 잰 값이 아님).
> DB는 Neon HTTP라 **쿼리 하나 = HTTPS 요청 하나(약 0.05~0.2초)** 입니다. 지연은 대개 '차례로 기다리는 DB 왕복 수'로 정해집니다.

## 1단계 (v3.91, 반영)

- **서버가 새로 뜰 때 생성문 37개를 하나씩 보내던 것** → DB에 남긴 스키마 지문이 같으면 조회 한 번으로 건너뜀(`game/server/db.ts` ensureSchema). 문장 목록이 바뀐 배포에서만 전부 돌림. 새로 뜬 서버의 첫 요청 약 2~7초 → 약 0.1초.
- **제단 정보(GET /api/altar)**: 차례로 기다리는 DB 왕복 6~8번 → 2~3번.
  - 세이브 전체 읽기 삭제(화면은 기여도 · 순위만 쓰고, 도전 시각 · 익명 여부는 자기 세이브에서 읽음).
  - 누적 기여 · 순위를 요청마다 전체 합산하지 않고 15초 공용 캐시의 전체 합계에서 셈.
  - 공용 정보와 내 이번 주 기여, 이번 주 순위와 월드보스 카드, 월드보스 요약과 내 순위를 함께 읽음. 이번 주 순위표 안이면 순위를 세지 않음.
- **전투 화면**: 재생 프레임(한 턴에 여러 번)마다 능력치(`stats`)를 3번 다시 계산하던 것을 동기화 때 한 번으로. 채팅 · 소식 · 시간당 효율 카드는 프레임마다 다시 그리지 않음(memo).

## 2단계 (v3.92, 반영)

- **게임 동기화의 제단 상태**: 공용 정보를 '핵심(제단 · 게이지 · 월드보스)'과 '순위(이번 주 순위표 · 전체 누적)'로 나눠, 동기화는 핵심만 읽습니다. 사냥 중 15초마다 전체 누적 합산(GROUP BY)을 돌리던 것이 없어집니다.
- **저장 공통 경로(mutate)**: 이벤트 · 정답 키 · 해킹 설정과 첫 세이브 읽기를 함께 읽습니다(캐시가 비었을 때 차례 대기 최대 4번 → 1번).
- **행동 응답의 기록**: 동기화처럼 버튼 행동에도 마지막 기록 키를 보내, 서버는 그 뒤 기록만 보냅니다(키를 못 찾으면 전체).

### 2단계에서 남긴 것
- 설정 읽기(이벤트 · 닫힘 · 해킹 · 비공개 · 정답 키)를 `WHERE key IN (...)` 하나로 합치기, `refreshEvents`의 게이지 중복 조회, 동기화 뒤 `buildCatalog`의 비공개 설정 조회, `postPlayerNews` 차례 쓰기.

## 3단계 (v3.93, 반영)

사냥 중 동기화(3~9초)마다 새 상태가 오면 열린 화면이 통째로 다시 계산되던 곳들입니다. 결과는 그대로이고 계산 횟수만 줄였습니다.
- **스킬 화면**: 성장표(`skillGrowthStages`)를 스킬 객체로 캐시(WeakMap). 검색은 `useDeferredValue` + 검색 중일 때만 만드는 검색 문구 Map, 정렬 키는 스킬마다 한 번. `SkillCard`는 `memo`, 성장표는 자세히 볼 때만. 누적 비례 패시브만 진행도 집계(`passiveGrowthBonus`에 집계를 넘길 수 있음).
- **장비 보관함**: 교체 미리보기(장비마다 `stats()`)를 모듈 캐시 한 칸에 두고, 장비 · 가방 · 레벨 · 직업 · 스킬 · 능력치 · 연구 지문이 같으면 다시 쓰지 않음.
- **업적 · 목표**: `progressReader(s)`로 같은 진행도 함수는 상태마다 한 번(`syncAchievements`도 사용). `achievementById`는 Map.
- **도감**: 지역 묶음을 `LazyDetails`로(펼칠 때만 그림). `FISH.find` · `[...ENEMY_SKILLS, ...SKILLS].find` → Map.
- **랭킹**: 시계를 결투 대기 중 1초 · 평소 10초로, 정렬은 `useMemo([rows, sort])`.
- **직업 화면**: `statusReader(s)`(상태 객체별 WeakMap)로 직업마다 조건 판정 한 번. 빠른 찾기 · 계보 요약 · 상세 · 비교가 함께 씀. 검색 결과 메모. 서버 · 시험처럼 상태를 고쳐 쓰는 곳은 그대로 `jobStatus`.
- **잔손질**: `format()` · `short()`는 공용 `Intl.NumberFormat`, 전투 기록 해석(`combatFxFromLog`)의 스킬 이름 찾기는 Map.

### 3단계에서 남긴 것
- 장비 보관함의 '보이는 줄만' 그리기(가상 스크롤): 캐시로 동기화마다의 재계산은 없어졌고, 장비를 바꾼 직후 한 번은 여전히 가방 전체를 계산합니다.
- 업적 화면의 닫힌 묶음 그리기(진행도 계산은 줄었고, 카드 수는 그대로).

## 4단계 (v3.94, 반영)

- **랭킹**: `listRankings`가 모든 시즌 · 게시판 행의 스냅샷 JSON을 풀어 season을 비교(전체 훑기) → 같은 식 `((snapshot::jsonb->>'season')::int), rating DESC, power DESC`에 인덱스. 실패해도 서버가 멈추지 않는 '선택 문장'(`OPTIONAL_SCHEMA`)으로 둠(스키마 지문에 포함 → 배포 때 한 번 만듦). 로컬 Postgres 16, 3만 행 · 30시즌: 39ms(전체 훑기 + 정렬) → 0.17ms(인덱스, 정렬 없음).
- **길드**: 정보 4번 차례 대기 → 2번(소속 + 순위표, 길드 + 길드원), 기부 · 기여 올리기의 길드 · 길드원 갱신을 함께, 목표 받기의 길드 · 길드원 · 내 수령 기록을 함께.
- **해커 조직 열기(GET /api/crew)**: 저장된 세이브만 읽고 답함. 소속 확인 주기(`CREW.refreshMs`)가 지났을 때만 저장 경로(mutate)로(게임 동기화도 `syncCrew`를 돌림).
- **채팅 보내기**: 채널 판정 · 마지막 전송 시각 · 세이브(이름)를 함께(3번 → 1번).
- **제단 바치기**: 축복 단계 올리기(`levelBlessing`)가 단계마다 게이지 전체 읽기 + 조건부 UPDATE(마지막 실패 포함 최악 24번) → 게이지는 처음 한 번, 이후엔 UPDATE가 돌려준 행(`RETURNING level, until, points, high_until`)으로 계산. 공물이 모자라면 UPDATE를 보내지 않음(평소 바치기 2번 → 1번). 겹쳐서 빗나가면 한 번만 다시 읽음.
- **금고**: 넣고 꺼낸 뒤 지갑을 다시 읽지 않고 메모리 값으로 답함.
- (화면) 모바일 장비 보관함 '등급별 일괄판매 · 분해': 공용 `.button-row>*{flex:1;min-width:0}` 때문에 줄을 바꾸지 않고 버튼이 약 35px로 줄어 글자가 넘침 → 칸 격자(`minmax(96px,1fr)`).

### 남은 것
- 2단계에서 남긴 설정 읽기 합치기(`WHERE key IN (...)`), `refreshEvents`의 게이지 중복 조회, `buildCatalog`의 비공개 설정 조회, `postPlayerNews` 차례 쓰기.
- 제단 바치기 뒤 `altarInfo`가 순위(boards) 캐시를 무효화해 GROUP BY를 다시 돌림 → 내 기여만 캐시에 더해 갱신하는 방식은 순위 계산이 얽혀 있어 보류.
- 공용 `.button-row` 규칙(`flex:1; min-width:0`)을 쓰는 다른 줄도 버튼이 많으면 같은 증상이 날 수 있음. 보이는 대로 개별 수정.

## 5단계 (v3.104, 반영): 서버 CPU(Vercel Active CPU)

1~4단계는 '기다리는 시간'(DB 왕복)을 줄였습니다. Active CPU는 DB를 기다리는 동안은 세지 않으므로, 여기서는 **서버가 실제로 계산하는 시간**을 줄였습니다.
측정은 `scripts/lib/reference-body.mjs`의 기준 몸(환생 5~100)으로 로컬 Node에서 잰 값입니다.

### 무엇이 CPU를 쓰나
- 서버는 지난 동기화 이후 흐른 시간을 2초당 1턴으로 전부 계산합니다(탭을 숨긴 시간 · 접속을 끊은 시간도 다시 들어오면 부재중 정산). 그래서 CPU ≈ **모험가 수 × 흐른 게임 시간 × 턴 하나의 비용**이고, 동기화 간격과는 거의 무관합니다.
- 요청마다 고정 비용(세이브 읽기 · 저장 gzip · 카탈로그 · 응답)은 약 5~6ms. 턴 하나는 잘 키운 몸에서 4~8ms였고, 그중 약 3/4이 `stats()`(능력치 계산)였습니다. 한 턴에 `stats()`를 13번가량 같은 상태로 다시 계산했습니다.
- 6시간 부재중 정산(10,800턴)이 잘 키운 몸 하나에 40~90초.

### 바꾼 것(전투 결과는 같음)
같은 난수로 기준 몸 14가지 · 825턴을 돌린 최종 세이브 해시가 전후 모두 같은지 확인했습니다(63초 → 24초, 약 −61%).
- `effectiveSkill`: 스킬 객체 · 레벨 · 숙련 단계별 캐시(WeakMap). 캐시한 객체는 동결(freeze)합니다. 고쳐 쓰던 `combat.ts`의 두 곳(`skillOf` · `pickActive`)은 복사본에 배율을 곱합니다.
- `regionThemes`: 지역 · 단계별 효과 객체를 한 번만 만듦. `regionFish`: 지역별 배열 캐시. `regionResearchStage`: 할당 없이, 결과가 정해지면 바로 끝냄.
- 같은 상태의 `stats()` 재사용: 처치 보상의 골드 · 경험치 배율과 황금 개체 확률, 처치 후 회복, 변종 확률(`variantChances`), 업적 진행도 읽기(`progressReader` 한 번 동안 최대 체력 · 마나 업적).
- 무리 드롭 판정: 판정마다 `dropRate`(= `stats()`)를 다시 계산하던 것을, 드롭이 바꿀 수 있는 값(골드 자릿수 · 물건 도감 수 · 가방 · 정수)이 그대로면 재사용.
- 전투용 캐릭터의 숙련 단계 · 연마 숙련 표: 턴마다 숙련 기록이 있는 모든 스킬(수백 개)을 계산하던 것을, 전투가 조회한 스킬만 계산(`lazySkillMasteryRanks` · `lazyRefinePractices`).

### 부재중 정산 표본 환산(게임 규칙 변경, `systems/offline-sample.ts`)
- 1,200턴(40분)이 넘는 부재중 정산은 워밍업 300턴 + 측정 900턴을 실제로 돌리고, 남은 턴은 측정 900턴의 증가분을 비례해 더합니다.
  - 워밍업: 정산은 체력 · 마나가 가득 찬 채 시작해 첫 사망이 평균보다 늦으므로, 처음 10분은 비율에서 뺍니다(버티기 힘든 사냥터의 사망 · 회복 대기가 비율에 들어감).
  - 비례에서 빼는 것: 일회성 보상(목표 · 모험 안내, `offline-tally.ts`)과 측정 구간의 희귀 처치(칠흑 · 까미 · 누리 · 별빛)로 얻은 양 전부(`markOfflineRare` · `noteOfflineRare`).
  - 희귀 출현: 측정 구간의 판정 수(`offlineTally.onyxRolls` · `specialRolls` · `variantRolls`)를 비례해 남은 시간의 판정을 실제 확률(칠흑은 출현 천장 포함)로 굴리고, 나온 몬스터는 `spawn(s, rng, force)`로 세워 `tick`으로 실제 전투. 까미 숙련 로또 · 누리 경험치 · 별빛 세계석이 표본에 걸렸는지에 따라 ×k로 흔들리던 편차가 없어짐.
  - 환산하지 않고 전처럼 분할 정산(`CATCH_UP_CHUNK`): 던전 · 랜덤게임 · 해커, 표본 중 사냥터 · 직업 · 환생이 바뀐 경우, 측정 구간에 레벨이 2 이상 오른 경우(막 시작한 캐릭터처럼 성장이 빨라 표본이 뒤를 대표하지 못함. 이런 캐릭터는 턴이 가벼움).
- 6시간 정산(레벨 100 기준 몸): 약 24~37초(요청 8번) → 2.8~4.4초(요청 1번).
- 끝까지 계산한 결과와 비교:
  - 6시간, 난수 한 벌: 골드 · 처치 · 숙련 · 도감 94~111%.
  - 시드 여러 벌 합계: 용의 둥지 난이도 0 · 40에서 사망 24/24 · 502/484(처음부터 끝까지 사망 비율이 일정함), 아케인 서식지에서 칠흑 격파 35/40 · 8/9(희귀 출현 일반화 전 측정).
- 장비는 남은 가방 칸까지 분해 정수, 넘치면 골드입니다. 그래서 정수가 더 많고 장비는 없습니다(칠흑 · 유물 · 계승 장비는 환산에서 뺌).

### 그 뒤 턴 하나의 비용
같은 기준 몸에서 3.9 · 7.9 · 8.3ms → 1.3 · 3.2 · 3.4ms. 남은 비용은 여전히 `stats()`(한 턴 5번 안팎)가 가장 큽니다.

### 남은 것
- 한 턴 안에서 처치 보상 → 업적 확인 사이의 `stats()` 재사용(사이에 바뀌는 값을 다 따져야 해서 보류).
- 업적 ‘최대 마나’를 아직 못 이룬 캐릭터는 턴마다 `stats()`를 한 번 더 부릅니다.

## 6단계 (v3.127): 요청 수 줄이기 · 플랜 용량

운영 수치: Vercel Fluid Active CPU가 하루 41분(모험가 4명이 아침부터 저녁까지). 어드민 페이지는 버튼을 누를 때만 요청하므로 원인이 아닙니다.
아래는 기준 몸(`scripts/lib/reference-body.mjs`)으로 로컬 Node에서 동기화 요청 하나(세이브 풀기 → 마이그레이션 → 턴 → act(sync) → 직렬화 · 압축 → 응답 직렬화)의 CPU를 잰 값입니다. Vercel의 vCPU는 이보다 2~3배 느린 것으로 보입니다(측정값 × 2~3 ≈ 운영 수치).

- 간격과 무관한 **고정 비용 약 4.5ms**(풀기 · 파싱 1.4 + 직렬화 · 압축 2.6 + 응답 0.6) + **턴당 3~5ms**. 3초 동기화에서는 턴이 1.5개뿐이라 고정 비용이 요청의 절반 가까이였습니다.

- 턴 비용은 여전히 `stats()`(포함 46%, 자체 22%)가 가장 큽니다. 5단계에서 캐시를 넣은 뒤라 더 줄이려면 턴 안에서 상태가 바뀌는 지점을 모두 따져야 해 보류.

## 7단계 (v3.129): 능력치 계산(`stats()`) 경량화 — 결과 동일

6단계 뒤 턴 비용의 65%가 `stats()`였습니다(한 턴에 5번: 턴 시작 · 처치 보상 · 드롭 확률 · 다음 몬스터의 변종 확률 · 업적 진행도). 호출 수를 줄이는 캐시는 입력이 넓어(골드 자릿수 · 처치 수 · 도감 · 가방 속 칠흑 …) 처치 한 번에도 값이 바뀌므로 두지 않았고, **함수 안의 중복 계산과 할당만** 없앴습니다.
